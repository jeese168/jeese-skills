# 审查发现的组织方式

适用于用户明确要求审查代码、配置、文档或 Skill，并希望知道哪些地方存在问题、问题为什么成立以及建议怎样修改。本 reference 只规定审查结果怎样被核实和交付，不授权修改被审查对象。

下面的文件名、源码标识和场景只用于少样本校准，不表示当前工作区或目标项目存在同名对象，也不能作为项目事实使用。

## 按审查对象选择判断标准

先确认用户要审查的对象、使用环境和已经明确的目标，再选择能够决定它是否有问题的标准：

- 审查文字规则、提示词或 Skill 时，核对用户已确认的意图、项目实际名称和结构、上下文中的语义一致性，以及它是否会误导读者或 Agent 形成不存在的对象、关系或行为。
- 审查成熟团队项目的代码和配置时，同时考虑正确性、安全性、项目明确规则、附近同类实现、兼容性和团队维护成本。现有惯例能够证明项目希望保持什么，但不能覆盖已经证实的错误或风险；反过来，也不应只因理想化的通用标准就把与项目协调且没有实际问题的做法报告为缺陷。
- 审查个人维护或从零开始的代码时，根据当前目标、正确性、简洁性、可维护性和可预见的变更成本判断，既不用不存在的历史包袱降低标准，也不为了看起来完整而引入当前任务不需要的企业级结构。
- 审查成熟团队项目的长期文档时，核对事实、预期读者、项目实际术语与结构，以及文档与代码、配置或团队流程的一致性。
- 审查临时调查记录或交接材料时，重点判断事实与未验证边界是否清楚，以及信息是否足以支持后续继续调查或接手；不按长期文章的完稿程度审查一份本来就为短期使用的记录。

项目惯例、用户明确标准和对象本身的正确性要求都是判断材料，它们在不同对象中的权重不同。审查结论应说明它依据了哪一种实际标准，不把某一类对象的标准套到所有任务上。

## “存在若干命名问题”无法支撑审查结论

反例：

> ## 命名问题
>
> 文档中有些概念没有定义，建议统一命名。

这段话没有说明问题出现在哪个文件、哪个原句使用了什么名称、仓库实际存在的对象是什么，也没有解释为什么读者或 Agent 会被误导。用户只能重新完成一遍审查，才能判断结论是否成立。

## `docs/setup.md` 用“运行配置中心”代替实际的 `config/service.yaml`

假设 `docs/setup.md` 写着：

> 服务启动时从运行配置中心读取超时参数。

同一项目实际只有 `config/service.yaml` 文件和负责加载它的 `ServiceConfig`，没有名为“运行配置中心”的组件、目录或正式概念。这里的问题不是措辞不够优雅，而是文档创造了一个看似存在的系统对象，读者可能继续寻找它，Agent 也可能围绕它生成新的目录或设计。

建议把原句改为：

> 服务启动时从 `config/service.yaml` 读取超时参数，并由 `ServiceConfig` 保存加载后的配置。

这个发现以具体文件和原句为对象，给出仓库中实际存在的文件与源码标识，说明误导会造成什么影响，再提供能够直接审核的替换文本。

## 每个标题对应一个可独立判断的问题

标题直接写明具体对象和已经确认的问题，例如“`docs/setup.md` 使用未定义的组件名”。高度相关的证据、影响和建议放在同一部分；真正独立的问题再分开，让用户可以按标题逐项同意或反驳。

引用原文时保留决定含义的最小完整上下文。原文太长时，引用关键片段，并说明相关前文或后文怎样补充、限制或改变它的含义。陌生英文先解释中文含义，再据此形成判断。

区分以下结果：

- **确认问题**：实际文件和上下文已经足以证明问题成立；
- **风险或歧义**：可能误导，但是否需要修改取决于项目约定或用户选择；
- **排除项**：表面可疑，核对定义或上下文后不构成问题；
- **未验证项**：缺少必要文件、运行证据或比较基线，暂时不能下结论。

建议应直接对应当前问题。文字问题可以给出建议替换后的完整句子；代码问题应说明建议改变哪个行为、影响哪些调用方以及需要怎样验证。不要借一次局部审查扩张成无关的全仓库重构。

没有发现问题时，说明实际审查范围和验证依据，不为了让报告显得有价值而制造低置信度发现。
