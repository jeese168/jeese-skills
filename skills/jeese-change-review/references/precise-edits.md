# 精确修改的交付正反例

这个虚构例子只展示怎样交付一处已经完成的代码修改，不代表任何真实仓库，也不是必须逐项复刻的输出模板。

## 只给修改结论无法完成审核

反例：

> ## 重试逻辑已经优化
>
> 重试次数现在可以通过配置控制，使用起来更加灵活。相关测试已经通过。

这段话没有说明修改发生在哪个文件、原来由谁决定重试次数、读取的是哪项配置，也没有给出测试范围。用户只能重新查看差异，才能判断“可以配置”是否真的按讨论结果实现。

## `runtime/retry.go` 将固定次数改为读取服务配置

假设 `runtime/retry.go` 的 `NewRetryPolicy` 原来直接写死三次重试：

```go
func NewRetryPolicy() RetryPolicy {
    return RetryPolicy{MaxAttempts: 3}
}
```

修改后，构造函数接收已经完成校验的服务配置：

```go
func NewRetryPolicy(cfg ServiceConfig) RetryPolicy {
    return RetryPolicy{MaxAttempts: cfg.Retry.MaxAttempts}
}
```

`ServiceConfig` 是进程启动时加载的服务配置；其中的 `Retry.MaxAttempts` 已经在配置解析阶段检查为正整数。因此，这次修改只改变重试策略从哪里取得次数，没有在 `NewRetryPolicy` 中增加第二套校验，也没有改变退避时间和可重试错误的判断。

对应测试覆盖了默认值和自定义值两条路径：没有提供配置时仍得到三次重试，设置为五时得到五次。这里应该报告实际执行的测试命令和结果；如果只检查了代码而没有运行测试，就直接说明尚未运行，不能写成“测试已通过”。

这个交付单元把文件、符号、修改前行为、修改后行为、相邻配置职责、未改变的边界和验证放在同一个解释中。标题本身已经说明实际修改，用户可以直接围绕这一项判断是否符合预期。

## 原文或代码太长时保留决定含义的上下文

如果 `NewRetryPolicy` 周围还有几十行退避和错误分类代码，不需要粘贴完整函数。可以只引用读取重试次数的片段，同时说明其余逻辑仍由原有字段控制。省略代码的依据是它没有参与本次修改，而不是因为它位于引用范围之外。

位置说明只能放在对象确定以后。例如“这个构造函数位于配置加载之后”不能代替文件名和符号名；应先说明“`runtime/retry.go` 的 `NewRetryPolicy` 读取已经校验的 `ServiceConfig`”，再补充调用顺序如何保证配置可用。
