# Markdown 格式习惯

格式必须服从文章的语义结构。以下规则来自主体语料中的稳定模式，不是要求每篇文章把所有形式都用一遍。

## 标题层级

个人技术文章默认使用：

```text
# 整篇文章标题
### 相对完整的主题模块
#### 可以独立讲清的知识单元
##### 知识单元内部的方案、类型、阶段或实现路径
```

通常跳过 H2。只有文章确实包含多个跨度很大的上位部分，而且每部分下面又有多组 H3 时，才增加 H2。不要使用 H6。目标项目已有明确层级约定时，以项目约定为先。

标题是正文的高密度索引，直接压缩当前模块的具体对象和已经形成的判断、动作或结果。读者只看标题就应知道本节讲什么，并能用它检查正文是否围绕同一个中心展开。同一层标题保持相近的语义粒度和表达方式；较高层标题可以因聚合多个内容而更抽象，越接近具体知识单元，越要说清实际对象或问题。

说明、复盘和修改记录已经形成结论时，优先使用陈述式标题。只有问题本身已经精确限定对象，而且正文确实围绕它给出答案时，才使用问题式标题；不要把已经知道的结论改写成宽泛的“从哪里来”“怎样配合”或“如何约束”来制造阅读悬念，也不要把面试问题逐题搬进文章形成问答骨架。标题文字外不再套加粗。

较高层标题为了聚合内容而比较抽象，单靠标题不足以让读者确定本部分范围时，可以紧接一行 Markdown 块引用形式的“注”，用白话说明这里讲什么，以及读完应能回答哪个具体问题：

> **注：**这一部分先说明 Entity 在三个运行端分别是什么对象，以及它们怎样对应。

“注”承担标题下的定位作用，不是每节必有的固定开场。标题已经足够具体，或后文只有一个简单知识单元时，不再重复说明。

一个标题下面必须有足以构成独立模块的内容。两个标题表达同一件事时合并；只有一句解释时通常不再增加层级。

## 段落与空行

正文段落、标题、列表、表格、代码块和图片之间保留一个空行。不要用三四个连续空行模拟卡片分隔。

一段通常承担一个主要认知任务，但相关思想应保持连续。不要把每句话单独成段，也不要把正常路径、异常路径和适用边界塞进一个超长段落。

## 列表与编号

先用正文给出概念或总判断，再使用列表拆开结构，必要时在列表后给出取舍或结论。

- 无序列表用于并列原因、特征、组成部分、优缺点和适用场景。
- 有序列表用于真实的执行步骤、阶段、优先顺序或连续方案。
- 嵌套通常不超过一层；如果一个子项需要多个段落，升级为 H5。
- 列表项需要能回答同一问题并保持同一语法粒度。

没有并列关系时不用无序列表；没有顺序时不用编号。不要用四个形容词代替对机制的解释。

## 表格

表格用于同一组字段下的比较或映射，例如：

- 方案—机制—优点—代价—适用场景；
- 状态—含义—后续动作；
- 组件—职责—实现；
- 角色—权限—产生的结果。

表格前说明为什么比较，表格后给出选择、边界或继续解释。三两句普通叙述不必造表；不要在一个单元格里塞多个长列表。

## 加粗与行内代码

加粗最小必要语义单元：短概念、并列标签、比较维度、关键条件或决定性结论。列表中可以使用 `**标签**：解释`。整句加粗只用于少量核心结论或警告；不要整段加粗。

行内代码用于类名、方法名、参数、命令、配置键、文件名、协议字面量、状态值和 API。普通中文术语不使用反引号。

## 代码块

代码块用于可复制代码、SQL、配置、命令输出、数据结构示例或精确的伪执行流程。已知语言时必须添加语言标签。

代码前说明它要证明或完成什么，代码后指出关键行、运行结果或理解边界。不要孤立粘贴一大段代码代替正文。

## 图片、Mermaid、PlantUML 与引用

图片、Mermaid 和 PlantUML 用于架构、流程、状态迁移、层级、调用链、UI 操作或复杂数据结构。简单枚举不需要画图。正文应说明读者需要从图中观察什么。

先选择能够清楚表达关系的最低复杂度形式：

- 节点和分支较少的简单流程、关系或状态变化，优先使用容易维护和直接渲染的 Mermaid。
- 标准软件图需要较多参与者、消息、分支、状态、类关系或活动节点，Mermaid 自动布局已经产生交叉、拥挤或语义混乱时，使用 PlantUML。
- 需要表达的不是严格节点—连线关系，而是空间、场景、概念组合或定制化说明图，并且没有合适的现成图片时，才使用可用的图片生成工具。技术结构、标签和文字需要人工核对，不能让生成图片虚构系统事实。

工具选择服务于可读性，不按“简单就不专业、复杂就更高级”的想法升级。能由一小段正文讲清的内容不画图；需要精确复现的系统关系优先使用可维护的文本图，而不是生成图片。

PlantUML 图写入项目时，如果目标项目允许保留图源，保存可编辑的 `.puml` 或等价源码；文档可以引用渲染后的 SVG 或 PNG，但不要只留下无法维护的截图。源码和渲染产物的位置仍服从目标项目约定。

为 GitHub Markdown 使用有信息量的 alt。若目标项目已有 `images/` 目录，语法例如：

```markdown
![图中展示的对象或关系](images/架构关系.png)
```

示例路径只表示写法，实际写入时应替换为目标文档中真实存在的相对路径。

不要混用 Obsidian `![[...]]` 与标准图片语法，除非目标项目明确依赖 Obsidian。

引用用于外部原话、重要限制、警告、旁注或需要与作者正文区分的材料。普通结论仍写正文。多行引用的每一段都要保持合法的 `>` 结构。

## 发布前清理

删除以下面试笔记残留：

- `Q:`、`A:`、追问和场次编号；
- 标题后的星号、难度、来源站点和“JavaGuide”等标记；
- TODO、待补充、进度复选框和私人对话链接；
- 空标题、只有标题没有正文的章节；
- 无意义的 `img`、`image` alt；
- 无语言标签的已知代码块；
- 连续多空行和粘贴造成的重复内容。

写入已有项目时，先检查该项目对文件扩展名、YAML front matter、图片目录和链接格式的约定。没有明确约定时使用普通 `.md` 和标准 Markdown 相对路径，不凭空引入某个笔记工具或发布系统的私有格式。
