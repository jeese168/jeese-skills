# 把必要内容解释清楚

用于阶段中实际写出概念、机制或设计说明。以本次文章目标和当前有效的内容为基础，形成后面能直接使用的解释。

## 找到理解缺口

读者见过名称不等于理解。先判断哪些概念不说明就会妨碍阅读；陌生源码标识配简短自然的中文名称或角色说明，再保留准确标识供对照。已有明确中文含义的局部变量自然使用，不硬造译名。

先写定义或能回应问题的结论，再按实际缺口选择解释内容：

| 内容 | 何时需要 | 写清什么 |
| --- | --- | --- |
| 定义与区别 | 不清楚对象是什么，或与相近概念混淆 | 实际含义及与当前比较对象的区别 |
| 作用与必要性 | 不清楚为何在本文出现 | 解决的问题及与当前任务的关系 |
| 关系与机制 | 不清楚过程或结果怎样发生 | 谁在何种条件下做什么，状态怎样变化 |
| 具体例子 | 抽象关系仍难以理解 | 输入、动作、变化和可观察结果 |
| 条件与边界 | 条件不同会改变判断 | 解释何时成立，依据支持到哪里 |

相互依赖的内容连成自然段，真正并列或需要对照时使用列表、表格。位置、角色、所有者和影响范围按理解需要自然融入，不给每个概念重复填写坐标清单。依据和理由沿用 [evidence.md](evidence.md) 的区分。

例如：“加载版本号区分同一对象的不同加载批次。对象重新加载后版本改变；旧请求返回时仍携带旧版本，因此结果会被拒绝。”这段解释可以被后续正文使用。“加载版本号：检查版本，后面展开”仍未完成解释。例子只示范写法，实际内容以当前材料为准。

## 递归补足必要前提

解释 A 必须先懂 B，就实际写出 B 所需的解释；B 又依赖 C 时，再判断 C 是否阻断本次理解。到有依据确认的读者基础、或足以支撑本次目标的位置停止。

学习文档按本次层次展开：高层说明定位和整体关系，中层说明协作机制，底层在主问题上对应实现和依据。相邻机制补到能理解作用；主线需要下钻时说明为什么这层机制影响当前结论。确需扩大已约定的目标或层次时，说明具体原因并询问。

技术方案同样需要必要前提。围绕当前问题和设计，解释对象、改法、作用、选择依据和成立条件；新对象、新关系或新行为在依赖它们之前讲清。无需把方案写成全套项目教材，也不能用另一个陌生名词代替解释。

## 保存实际说明并检查

在当前阶段保存已经写清的段落、关系、过程或例子，保留与依据的对应。概念独立时可以分别记录，紧密依赖时连成完整机制说明。早期不必采用最终文章顺序，后续组织阶段再安排位置。

完成前检查：关键前提是否已有说明，是否只是重复名称，因果与条件是否连贯，例子是否帮助理解，是否夹入本次用不到的功能清单。必要缺口继续补；事实变动回到依据更新。中间记录是成文材料，最终文章仍须在合适位置呈现读者需要的解释。
