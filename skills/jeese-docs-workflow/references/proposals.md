# 技术方案的内容与判断

用于形成、维护或合并技术方案、设计文档和 PRD。沿用本次需求、已确认范围及项目文档结构；完整程度以执行 Agent 或其他协作者开展本次工作所需的信息为准。

## 从现有项目形成设计

先看实际需求、相邻实现、已有模块和稳定惯例。明确当前问题与目标差异，优先考虑能解决问题的既有能力。解释推荐时说明当前规模、真实限制、依赖、引入成本和失败影响；重要架构、成本或风险选择留给用户决定。

已有讨论中确认的设计直接采用，核对仍然适用即可。讨论过但未接受的候选先留在工作记录中，提出具体差别、推荐及依据后继续讨论。整理或复核时自然发现的矛盾、缺口，或能复用现有能力且能明显改善正确性、可行性或维护成本的候选，也在文档外说明，由用户决定是否调整方案。

当未决部分影响本次交付时，结合上下文询问继续讨论后纳入，还是先交付已确定内容、将其延后或移出本次范围。明确安排直接遵循；延后与移出不自动成为未来必须完成的承诺。若本次实施依赖被移出的部分，说明具体影响再确定处理。

## 写清改法、作用和依据

应用 [概念与机制指导](concepts.md) 解释本次方案：现状怎样，准备怎样改，改法如何起作用，为什么选择它，作用在什么条件下成立。新增或修改的对象、接口、数据、状态或协作关系，按实际需要讲清，形成连续论述。

实际实现、可推导的作用、已有决定和预期收益分别按 [依据指导](evidence.md) 表达。新的设计理由可以来自当前需求和取舍，不能把假设收益写成实测，也不能编造旧实现的历史动机。

需要图时，按 [图文指导](visuals.md) 展示关键关系或过程，配套说明理由与条件。技术方案既要让人知道准备改什么，也要让人理解这些修改怎样一起满足需求。

## 供后续执行的信息

根据本次实际改动说明实施位置与范围、协作约定、成立条件、必要的异常或兼容处理及验证方式。这些信息按内容关系组织；项目模板已有位置时在对应位置讲清。

验证安排对应需求和设计中的可观察结果。尚未实施、测试或上线的内容按计划描述；实际检查过什么就报告什么。方案写作的完成状态与项目实现的完成状态分别记录。
