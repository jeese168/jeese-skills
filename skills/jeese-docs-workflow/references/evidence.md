# 整理有依据的写作内容

围绕本次文档目标读取已有讨论、资料、代码和文档。已核实且仍有效的材料可以复用；只有名称或片段不能证明完整行为时，继续查对应定义、调用、配置或来源。材料获取由实际问题决定。

## 先确定哪些内容成立

根据本次涉及的事实，区分现有实现、实际观测、依据材料形成的推断、建议和计划。学习文档保存当前稳定认识，技术方案说明现状与拟议设计，复盘保留真实发生的过程和验证结果。

来源路径、符号、位置、版本或条件记录到足以回查。一个来源可以支撑一段连续说明；重新使用时核对会变化的产品行为、配置和实现位置。引用保留决定含义的条件，陌生语言先解释含义，再用它支持判断。

事实不明时先用现有材料和可用能力核对，按证据限制表述或调整内容。遇到无法自行解决且影响结论的来源冲突，说明冲突及影响后询问。一般的材料是否足够由 Agent 判断和处理，不先抛出笼统的“还需要补充材料吗”。

## 把理由写真实

| 当前要说明的内容 | 依据及写法 |
| --- | --- |
| 项目要求与实现约束 | 回到需求、接口契约、项目明确约定或具体行为；同类实现只能先说明惯例 |
| 现有机制有什么用 | 说明实现可核实的作用和成立条件 |
| 原作者当初为什么这样设计 | 有对应设计记录或明确陈述时说明其依据；从实现推导出的合理用途仍是推断 |
| 本次为何选择一种改法 | 说明当前需求、已有基础、备选差异和取舍，区分用户已确认的选择与待讨论建议 |
| 性能或业务收益 | 实测保留基线、方法、样本和条件；预期收益说明推导依据及验证方式 |

例如代码显示缓存命中后跳过远端，可以据此说明减少一次远端读取；“当初为了高并发而设计”需要相应历史依据。新方案准备复用现有队列时，可以基于项目已有能力说明引入成本，但不能顺势编造吞吐提升数据。

## 产物应保留已经完成的理解

围绕实际内容写出有效结论、条件、关系和必要依据。说明缓存行为，就保留“本地缓存有效时直接读取，缺失或失效时访问远端”这样的具体内容；只记“已检查缓存模块”无法支撑后续解释。

技术指标冲突时保留差异并降低结论强度，判断变化同步到依赖它的解释。风格语料、示意代码和例子仅用于表达校准，项目事实来自本次实际核对。
