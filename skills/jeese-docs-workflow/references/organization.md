# 把内容组织成一篇文章

使用已经形成的实际解释、依据和设计决定，结合 [核心风格](core-style.md) 安排文章。内容尚未成立时先补足，组织工作处理内容之间的关系。

## 确定主线与阅读顺序

围绕本文读完要形成的认识或要支持的行动，选定一条主要推进方式。学习内容可沿对象关系、一次运行过程或共同维度展开；技术方案连接需求、现状、设计和实施效果。正式文档的章节沿用任务及项目约定，在既定章节内把论述连起来。

多处都依赖的背景集中说明一次，局部前提在使用处交代。一个概念所需的定义、机制和边界属于同一理解单元时，在所属位置讲清。查证顺序不必等于读者顺序；把探索中的误解和修正整理成实际对比、依据或边界。

段落之间有因果、条件、顺序、比较或例证关系时，把关系写清。流程按实际顺序，分类说明分类轴，比较说明维度。机制与解决的问题、效果和代价尽量相邻。只在新依据改变判断或进入新的抽象层次时重新解释同一观点。

## 留下指向实际内容的安排

写明哪些前阶段内容在何处使用、怎样合并或省去、关键段落如何衔接。难以连接的地方写出实际过渡，必要图示按 [图文指导](visuals.md) 形成图稿和配套说明。

例如整理异步请求笔记，可以先建立同一对象会多次加载、旧请求可能晚到的共同背景，再使用已写好的版本号说明，沿一次重新加载解释旧结果怎样被拒绝。版本更新的实现位置按本次层次展开。这种安排指向具体内容；“背景、原理、总结”尚不足以引导正文。

维护时说明新内容的自然归属及前后关系；合并时说明来源内容怎样组成统一主线。长期文档将相关补充融入原位置，临时汇总可以保留来源和时间顺序，只补足使其可读的关系。

## 核对组织是否成立

前提先于依赖它的内容，关键对象不会只出现在图或标题里。各部分能说明为什么接着出现，不让读者把互不相接的小节自行拼起来。必要解释不能只留在工作附录。缺少解释回对应内容阶段补，位置不合适在当前阶段调整；事实或设计改变时同时更新图文安排。
