# 针对性解答

用户在本次明确询问一个概念、某个关系或一点、几点疑问时使用。先回答实际问题，补足必要前提，让用户能继续读、继续问或继续做。不是把标准模式压成固定的短模板。

## 按所问范围处理

沿用对话已经建立的理解。用户问两个问题就分别解决，但紧密关联的原因和机制连在一起讲；不以问题数量判断必须换模式。用户明确指定完整分阶段模式时，回到指定路线，不能擅自用本路线省略阶段。源码带读中问某一点，先回答这一点，保留主线阅读位置，不自动继续下一段。

单个概念不强制落盘，不为它创建任务目录或先询问深度档。几个范围清楚的问题也不因凑齐形式而创建工作流；确实需要长篇重新组织时，可以建议标准或快速，但由用户决定是否切换。目的或问题本身有影响答案的歧义时，只问清这个缺口。

涉及需要补查的项目事实时读 [evidence.md](evidence.md) 并核对依据。出现尚未建立的关键概念时读 [concepts.md](concepts.md)，在当前回答中应用其解释方法，不运行该文件的阶段落盘要求。只有视觉材料更能说明所问关系时读 [visuals.md](visuals.md)。需要较长的组织或上一轮讲得不清时，读 [organization.md](organization.md) 中与当前卡点有关的写法，不执行标准路线。

用户明确追问某次 Bug 的局部判断时，可按需读取 [bug-evidence.md](bug-evidence.md) 或 [bug-diagnosis.md](bug-diagnosis.md) 核对这一点，问修改位置时再读 [bug-explanation.md](bug-explanation.md) 的相关部分；不因此新建一套阶段产物或调查无关链路。普通的代码语义问题不加载这些诊断指导。

## 自然回答

先给直接结论或定义，再解释使它成立的必要关系、原因或例子。首次使用陌生术语时说明其实际角色，不把另一个陌生术语当作解释。只有依赖运行位置、所有者或相邻对象才能理解时才补这些信息，不逐项填写系统坐标。

只修补当前卡点，不从头重讲整套系统。一个自然段能够讲清的，就用自然段；真正并列的疑问可以分项。不要制造宽泛标题、空洞总结或长括号嵌套，也不要省掉会改变结论的条件。

已经有任务目录时，只有追问带来的新事实、必要概念、纠正或范围调整会影响后续阅读与结论，才更新原来的记录和受影响图文；单纯换一种说法讲明白，不额外落盘。没有现成任务目录的独立小问题不为形式而创建目录。

追问发现先前答案有错时，直接说明更正并补依据。源码带读的阅读起点、停点和下一处位置要继续保留；用户说继续后回到原带读路线，只有范围改变才重新确认相关范围。最终产物是用户所问问题的答案，不是“已完成分析”的过程报告。

对照：用户只问“这个回调是谁触发的”，先核对并解释实际注册或调用，不从模块入口重讲。若查到先前误认了触发方，则同步修正已有阅读路径；若只是把已知回调关系讲得更通俗，回答即可。
