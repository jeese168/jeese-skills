# 组织诊断讲解与修改建议

用于标准第三阶段或快速第二阶段的 Bug 分支。先使用当前有效的现象、诊断及概念产物，需要补读时按路线约定取得相关区块，再用公共组织和视觉指导形成讲解。若根因已知，围绕已核实原因直接组织，不补造调查过程。

## 把表现与机制连起来

说明用户看见的表现怎样由相关条件、状态和调用产生。图适合展示正常路径与发生偏差的位置；假设路径明确标注，不能与已观测的轨迹混画。文字补足关键概念、约定和条件，不逐箭头复述。

确实发生过止损、临时绕过、根治和验证时，按因果交代它们的不同作用；没有发生的步骤不为完整而编造。仅提出方案时称为建议，不写成已实施或已验证。

## 需要修改建议时区分三个位置

只在用户本次需要修正建议或修改归属判断时展开：

- **表现位置**：QA 或用户在哪个功能、端或流程看见异常。
- **原因位置**：哪一段行为违反了预期或已经存在的约定，依据是什么。
- **候选修改位置**：在哪一处修改能解决问题，影响哪些调用方，当前推荐什么。

三者可以相同，也可以不同。先核对项目实际契约、调用行为和相邻实现，再用通用经验辅助，不能依据 QA 指派对象或岗位名称分配责任。根因未定位时，给出下一步需要哪一侧配合核实，不把候选边界当作已经确定的责任方。

存在多个合理修正位置时，围绕本次问题说明各自改变的行为、影响范围、兼容性和维护代价，再给出有依据的推荐。契约不明、需要跨端协商或涉及业务决定时，明确待决点及推荐依据，由用户决定或协调；Agent 不替项目成员拍板，不在讲解过程中自行改项目代码。

这与情况六不同：情况六中的概念说明、错误关系和图文修订由 Agent 自行处理；实际工程怎样修、由哪个模块承担，是本次诊断建议中的用户决策事项。

## 草稿与对照

中间产物应有实际的因果说明、图及配套文字；需要建议时写出具体建议与依据。下一阶段据此生成答案，不只留下“最后说明谁来修”的占位句。

反例：QA 在业务功能上触发异常，就建议业务开发者兜底修复；或仅凭模型经验认定状态问题总由服务端处理。

正例的判断方式：若已核实业务调用符合契约，而公共框架违反了自身回调约定，则说明业务功能是触发入口，优先建议框架层修正。若框架本来允许重复通知，而业务方遗漏了约定要求的处理，则建议可能相反。实际结论必须来自当前项目，不能把这两个示意当作预设答案。
