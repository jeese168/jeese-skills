# 对齐 Bug 问题与已有证据

用于标准或快速的 Bug 分支第一阶段。用户明确要求根据异常查原因或讲解故障时读取，不因源码里有错误分支就启用。

## 从实际问题开始

先用已有的 QA 描述、用户叙述、截图、日志、复现过程和源码确定：预期怎样，实际怎样，发生在什么操作和环境中。版本、配置、复现频率或时间点只有影响判断时才补问；已有信息足够就继续。

代码语义、实际观测和用户描述分别记录。源码能证明某个条件下会怎样，不自动证明这次运行走过该条件。用户已提供日志路径时，围绕本次对象、时间、请求或状态标识检索相关上下文；不要只截一条报错就丢掉前后因果，也不要倾倒整份日志给用户。

没有日志时先核对可用实现、预期约定和复现条件；必要时指出哪项观测最能区分候选原因。不要把缺日志当作无限停问的理由，也不要编造一次运行轨迹。安全且已获任务授权的复现或诊断可以用于补证据；修改代码以加日志、调整配置或实际修复不是单凭本 Skill 就获得的授权。

## 找到偏差所在的链路

沿与异常相关的输入、状态变化、消息或调用边界查证。跨客户端、服务端、业务模块和公共框架时，说明各对象实际职责和约定，先找数据或行为在哪一段开始不符合预期。

QA 把问题提给谁、表现在谁的功能上，都不是根因或修改归属的证据。版本、接口契约、真实调用和相邻可用实现比一般经验更能决定当前项目中的判断。

## 第一阶段产物与对照

在 `work.md` 留下可供诊断的预期／实际差异、已有复现条件、关键材料位置、已核实路径和剩余缺口。按实际材料用简短段落或必要的对照表组织，指出影响后续诊断的具体缺口。

反例：看见“客户端血条未刷新”，就写成“客户端刷新函数有 Bug”，或者因为源码有刷新回调，就写成“这次回调已执行”。

正例：记录已观察到血条未变化、相关代码在哪里、是否已有状态到达或回调执行的证据。接着定位最能区分“状态未变化／状态未到达／界面未刷新”的边界；没有证据的部分保持为待查对象，不自行选定一个根因。

这些是诊断情境下的查证要求。普通源码学习解释一个函数在给定条件下的行为时，无需为了证明代码语义额外索要日志。
