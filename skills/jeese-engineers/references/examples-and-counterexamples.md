# 正例与反例

这些内容是少样本提示，用来校正容易走错的那几步，不是需要复刻的固定话术。其中的场景、路径、源码标识和配置项都是虚构的，不表示当前工作区存在同名对象。

## 指定了就按指定、有材料就按材料

用户把审查窗口按条写好的发现贴回执行窗口，只加了 `/jeese-engineers`。上下文明确表明这是送回来的审查意见。

反例：因为没写「核实成三类」，就让用户再选一遍所有产物。

正例：结合材料和上下文，直接按情况四核实成三类。

用户写了「用 jeese-engineers 给我全量路径」。

正例：按指定走情况一，全量已经说清，不再问要交哪一种产物。

用户把情况二生成的完整指令与原文或路径拼好，交给审查窗口。即使仍在末尾附了 `/jeese-engineers`，任务也已由指令写清。

正例：审查窗口直接照收到的指令执行；不要求再次调用 Skill，也不把它归到独立文档核查的情况三。

## 只有点名时询问或按进度推荐

用户在输入框里只发了 `/jeese-engineers`，没有指定产物或其他材料。

反例：自己挑一种开始做；或每次都用同一句把所有产物列成选择题。

正例：停下来问这一轮要交什么。执行窗口刚改完代码、路径还没交时，可以顺带推荐先列落盘路径，并问增量还是全量。路径已经交过、下一步通常是生成审查指令时，推荐情况二。用户应了再做。

## 有材料但任务仍不明确时针对歧义询问

用户只加了 `/jeese-engineers`，贴来的文字是「重试配置可能缺少校验，建议统一在入口处理」。当前上下文无法判断这是要交给另一窗口审查的方案内容，还是另一窗口已经给出的审查意见。

反例：只因文字里有「建议」，直接当成审查结论分三类；或每次有材料都要求用户重新选任务。

正例：说明「这段看起来像审查意见」，再问「你是要我核实这条意见并分三类，还是为这段方案生成送审指令？」等用户确认。若上下文已经明确这是贴回来的审查结论，就直接核实分类。

## 送审与独立核查按用户要的产物区分

用户说：「这轮技术方案已经写完了，用 jeese-engineers 给我送审指令。」

正例：走情况二，按当前方案和任务背景生成完整指令，直接输出供用户复制。即使对象是 Markdown，也不直接审查它。

用户说：「用 jeese-engineers 检查 `/Users/demo/notes/power-design.md` 是否还符合现在的战力实现。」

正例：走情况三，读取文档和相关实现，直接报告差异、依据和建议。

反例：因为两条请求都有文档，就都交一份审查指令；或都开始核查文件。

## 独立核查文档需要明确意图

用户正在修改战力模块，只提到「旧方案可能没更新」，没有要求另做文档核查。

反例：自动切到情况三，开展整套文档维护审查。

正例：保持当前任务。用户之后明确说「单独核对这个方案是否仍适用」时，再进入情况三。若用户只贴一个绝对路径并点名 Skill，结合上下文仍判断不了要做什么，就询问用途。

## 文档与实现不一致时分别核对依据

用户独立核查一份写着「战力实时计算」的方案，当前代码使用缓存。

反例：只看见差异就认定文档过时，建议统一改成缓存。

正例：先核对方案状态和已确认的决定。若缓存方案已经批准且实现符合约定，指出旧段落需要更新；若实时计算仍是有效要求，指出实现偏离；若文档是未来改造提案，说明它描述目标状态而非当前实现。缺少决定依据时保留待确认项。

同样，用户指定的 OpenSpec 提案中某项尚未实施，不自动构成文档错误；外部资料描述新版本，也不自动推翻项目正在使用的旧版本说明。

## 未说明增量或全量时只问这一句

用户点名本 Skill，说「按 jeese-engineers 做完把路径给我」，没有说增量还是全量，前面也没说过。

反例：先猜一份全量清单，或先开始改代码，改完再问范围。

正例：只问这一句，例如「这一轮要增量还是全量（存量）？确认前我先不动文件。」等用户回答后再开始。

单独只要路径、同样没说增量或全量时，也只问这一句，问清再列清单。

## 落盘路径只收磁盘上的绝对路径并说明角色

本轮真正写到磁盘上的是 `/Users/demo/notes/checkin-reward.md` 和 `/Users/demo/shop/services/checkin/handler.go`。对话里还直接输出过一段未落盘的方案草稿。

反例：

```text
- checkin/handler.go
- 上面那份方案草稿
```

正例：

```text
范围：增量（本轮实际落盘）

- `/Users/demo/notes/checkin-reward.md`：本轮写入的签到奖励方案
- `/Users/demo/shop/services/checkin/handler.go`：本轮改过的签到发奖入口
```

## 增量只列这一轮实际落盘

用户要增量。这一轮只改了 `/Users/demo/shop/config/checkin.yaml`。同一功能里，昨天已经落盘的 `handler.go` 本轮没动。

反例：把昨天的 `handler.go` 和今天的 `checkin.yaml` 一起列出来，当成增量。

正例：增量清单只有 `/Users/demo/shop/config/checkin.yaml`，并说明它是本轮改过的签到配置。

## 全量按当前功能收齐相关落盘

用户要全量。对话主题是「签到奖励」，即便中间压缩过，仍能抓住这一需求。磁盘上与该需求相关的是方案、处理函数和配置；工作区里还有一份无关的本地实验文件 `scratch/tmp.json`。

反例：把工作区所有脏文件都列进去；或只列本轮刚改的那一个文件，却写成全量。

正例：列出签到奖励相关的方案、处理函数、配置的绝对路径，并标明全量。`scratch/tmp.json` 与该需求无关，不进清单。

## 单独只要路径时只交路径

上一轮已经改完文件，当时没有给路径。用户再说：「用 jeese-engineers，把刚才改的绝对路径给我。」或只要相对路径。

反例：再改一轮代码，或顺手写一份审查指令，或因为这一句里没有写「增量」就先去问全量还是增量。

正例：认出这是要刚才那次修改的落盘地址，按增量只交路径清单和角色说明。工作区内的文件用户只要相对路径时，给仓库相对路径；工作区外的文件仍给绝对路径。不会因为索要清单这一轮没有再写文件，就回答「本轮没有落盘文件」。

## 顺带点名时先完成正事再交路径

用户说：「按这个方案改签到发奖，并用 jeese-engineers 在做完后给我增量路径。」

反例：只回一份空的路径格式，正事还没做；或做完正事就结束，不交路径。

正例：先改该改的文件，确认已经落盘，再交本轮绝对路径和角色说明。

## 审查指令客观并写清本轮怎么审

用户要一份给审查窗口的指令。已确认需求是允许通过配置调整重试次数，同时保持默认三次及原有退避行为。执行窗口刚把重试次数改成读配置，选择在配置解析阶段统一校验；最大允许次数尚待产品确认。

反例：指令里写「重试次数改为读配置是正确的，请确认一下文案」，并把执行窗口的选择当成既成结论。

正例：指令带上配置可调、默认三次和退避行为保持的已确认要求；把「在配置解析阶段统一校验」写成执行方选择、请审查其是否覆盖所有调用入口，把最大允许次数标为待产品确认。写明被审对象形式和可核对的增量比较范围，请核对 `NewRetryPolicy`、调用方及默认值和自定义值的测试；按条写对象、问题、影响和建议，只在对话里报告发现。这些内容按任务组织成可粘贴的指令。

## 生成的指令带齐审查和回复要求

沿用上例。用户会自行附上本次文件路径，执行窗口已经确认本次变化限于重试策略及其调用处。

反例：只输出「检查重试配置，按 jeese-engineers 情况三回复」，让没有安装 Skill 的审查窗口无从知道具体要求。

正例：生成可直接粘贴的指令，例如：

> 请读取我附上的文件，审查本次重试配置改动。已确认需求是次数可配置、默认仍为三次、退避行为保持不变；最大允许次数待产品确认。本次增量是 `NewRetryPolicy` 从直接构造 `MaxAttempts: 3` 改为接收 `ServiceConfig` 并读取 `cfg.Retry.MaxAttempts`，以及调用处改为传入该配置。其余原有代码作为核对上下文。
>
> 执行方选择在配置解析阶段统一校验，请独立核对是否覆盖所有实际入口，以及框架初始化顺序是否保证先校验再使用。检查调用方是否正确传参、默认值和自定义值是否有相应测试，以及变化对相关调用的影响。发现其他变化或缺少比较材料时，说明范围缺口。
>
> 直接在对话里用简体中文逐项写发现：具体文件和符号、问题成立的证据、影响、建议及所需验证。区分确认问题和待核实风险；测试存在与测试实际通过分别说明。没有确认问题时，报告实际检查的范围和依据。保留被审文件原状，只交审查发现，三类处置由执行方随后核实。

这里只示范本任务所需的信息。其他任务应改写审查重点；相关框架和调用方即使未改过，也可能是验证本次变化必需的依据。

## 增量审查指令交代文件内部的比较范围

`handler.go` 昨天改了结算逻辑，今天改了重试，两部分都未提交。用户要审今天的增量。执行窗口有本次编辑记录和修改前片段。

反例：指令只写「审查 `handler.go` 的本轮增量」，让另一窗口自行猜范围；或把整个工作区 diff 当作今天的变化。

正例：路径清单仍只给绝对路径和角色说明；审查指令写明本次修改的是 `NewRetryPolicy` 及其调用处，并带上对应的前后片段或可访问的准确 diff。说明结算变化属于此前任务，可读取相关代码验证调用关系，发现范围限定在本次重试修改及其影响。

若只剩当前文件，现有差异也无法区分两次修改：说明已定位到文件，但缺少能划定本次变化的材料；向用户询问可用的比较版本或范围。用户确认改为全量后，再生成全量审查指令。

## 审查窗口只写发现的问题

用户把路径和审查指令拼好，贴进审查窗口。

反例：在审查结果里把条目分成「认可 / 不采纳 / 争议」；或直接去改 `handler.go`；或把发现写成文件。

正例：只按条写发现，直接打在对话里。例如核对方案对当前配置来源的定义和实际加载代码后，指出方案中的「运行配置中心」与已确认的本地配置来源不一致。

## 每一条发现都能单独点头或反驳

反例：

> ## 命名问题
>
> 有些概念没有定义，建议统一命名。

正例：

> ## `/Users/demo/notes/checkin-reward.md` 把当前本地配置来源写成「运行配置中心」
>
> 方案的「当前配置来源」段落已明确超时由本地 `config/checkin.yaml` 提供，本次也不改变配置来源；实际启动加载代码将这个文件读入 `ServiceConfig`。后文却写服务启动时从「运行配置中心」读取超时，与前文定义及实现不一致，会让实现方误以为还需要连接另一组件。建议改成：启动时从 `config/checkin.yaml` 读取超时，并由 `ServiceConfig` 保存。

## 路径清单未列出时先核对对象是否存在

用户提供增量文件清单，方案中提到配置中心，清单没有对应文件。

反例：因为清单里没有，就认定组件不存在，要求删去相关设计。

正例：先核对方案是否在描述现有组件或计划新增的能力，必要时读取相关定义和实现。确认语义与事实冲突时再报告问题；若资料不足，就说明尚未验证配置中心的存在或接入关系，以及需要哪项材料。

## 三类只能在自己核实之后划分

审查意见写：`handler.go` 没有校验重试次数，会接收到非正数。执行窗口核对配置解析和所有相关调用入口后确认，这条调用链上的次数已在解析阶段校验为正整数，`NewRetryPolicy` 只读取已校验字段。

反例：因为审查窗口写了「必须再校验」，就把这项放进认可，并立刻改代码。

正例：划入不采纳，指出解析校验及调用链的证据如何排除了「会接收到非正数」这个前提。认可类只放执行窗口自己查过、确认成立、且不需要再问产品或他人的项。两边都觉得该改、但还要问产品或客户端的项，放进争议、待用户判断。

## 证据不足时保留为待用户判断

审查意见担心重试函数存在绕过配置校验的入口。执行窗口确认主入口经过校验，但尚未核实一个外部调用方的约束。

反例：凭「我们一般都在上游校验」把意见放入不采纳，让用户略过。

正例：完成当前可做的核查后，将该项放入待用户判断，说明主入口已验证、外部入口还缺哪项证据。列出先确认调用约束和增加入口校验的做法及代价；给出有条件的推荐，例如先确认外部调用方是否保证合法输入，再决定是否增加校验。

## 核实后这一轮只整理三类

用户说：「把审查意见按 jeese-engineers 整理成三类。」

反例：在同一轮里按认可项改掉 `handler.go`，再回来写三类说明。

正例：只交三类分组。认可类写短。不采纳类写排除关键前提的证据。争议类写选项和推荐。等用户下一句下令，再处理用户点头的项。

## 争议类写清选项和推荐

审查窗口建议签到奖励在发奖当时扣库存。执行窗口看到现有结算是每天凌晨批量扣。这涉及产品规则。

反例：只写「这里有争议，请你决定。」

正例：写清分歧是「实时扣」还是「保持凌晨批量扣」；给出两种做法和各自代价；推荐在产品确认前保持批量扣，因为现有对账按日切；并标明这要用户问产品后才能定。

## 只问一点时只答那一点

用户问：「`NewRetryPolicy` 为什么不再自己写死三次？」

反例：从本任务所有改动文件讲起，再扩展到测试策略、以后怎么做配置中心、以及相关的设计原则。

正例：只讲 `NewRetryPolicy` 现在读取已经校验过的 `ServiceConfig.Retry.MaxAttempts`，所以次数改由配置决定，函数里不再写死三次。讲到这里停。用户下一句问测试，再答测试。

## 讲全并指定重点时完整回答

用户说：「把这次改动讲全，重点解释重试为什么这样改。」

反例：只答重试，把用户已经要求的整体说明留到下一轮再次索要。

正例：这一轮讲清本次相关改动，在重试部分详细说明原因和依据，其余部分按理解整体变化所需的深度交代。

用户说：「后面我要整理笔记，现在先告诉我重试为什么改成读配置。」此时只回答重试这个问题。

## 沉淀时按实际改动把相关部分讲全

用户说：「我要把这次签到奖励的改动整理进笔记，把相关改动讲清楚。」

反例：只凭对话印象说「发奖逻辑优化了，测试也过了。」

正例：按磁盘上的方案、处理函数、配置组织，写清各文件改前做什么、改后做什么、谁调用、证据来自哪份当前文件或哪次 diff。工作区状态和对话记忆冲突时，以磁盘和版本记录为准。

## 中间产物审查只在用户要求时启动

用户调用讲解 workflow，要求快速了解缓存更新过程，没有要求子 Agent 检查。

反例：因为存在 `work.md`，自动调用情况六；或每次问「这次认真审还是省 token」。

正例：原工作流自行生成和检查。用户明确补充「最后生成前用子 Agent 检查中间产物」后，在既定检查点调用情况六；不要求再点名 jeese-engineers，也不切成情况二让用户搬运指令。

## 子 Agent 审查前带齐理解目标

本次快速了解对象重载，只需达到协作与机制的深度。概念说明和图的草稿已形成，用户明确要求审查。

反例：只给子 Agent 一条文件路径和「看看讲清楚没有」；或告诉它「加载版本号解释肯定正确，只检查错字」。

正例：交代用户要理解为什么旧请求会被拒绝、已知道请求的含义但不了解加载批次，提供本次概念说明、图文草稿及对应依据。明确检查前提、关系和组织是否支持下一阶段，只返回发现，不修改文件，不要求展开整个对象继承树。

## 主 Agent 核实两类并直接修正

子 Agent 指出草稿只说「版本检查不通过」，未解释版本区分什么；同时建议增加所有父类的职责表。

正例：主 Agent 对照材料确认首个缺口，放入采纳并直接补上加载批次和旧请求的关系；父类表不影响本次理解，放入不采纳并说明依据。随后更新图例，核对本阶段条件，继续最终讲解。无需用户批准，也不改源码。

若子 Agent 断定「版本是在请求返回时才更新」，主 Agent 没有支持这个时点的证据，就不能照写。继续核对；依然无法确定时，保留时点未知并删除原文同样缺乏依据的确定说法。对建议的处置只有两类，事实的不确定性仍要保留。

## 没有独立审查结果不声称通过

用户明确要求独立审查，但当前环境无法创建子 Agent。

反例：主 Agent 自己检查后记为「子 Agent 审查通过」，或不说明就直接生成最终讲解。

正例：保留中间材料，说明独立审查没有完成及实际原因，不越过检查点。若用户之后撤销这次独立审查要求，才回到不带审查的路线继续。
