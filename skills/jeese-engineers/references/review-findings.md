# 审查判断与发现的组织要求

本文件供主 Agent 按用途选取指导：情况二生成送审指令时，将适用的审查要求写入交付文本；情况三直接核查文档时，按其 reference 的指引使用证据与输出要求。

对照少样本：[审查窗口只写发现的问题](examples-and-counterexamples.md#审查窗口只写发现的问题)、[每一条发现都能单独点头或反驳](examples-and-counterexamples.md#每一条发现都能单独点头或反驳)、[路径清单未列出时先核对对象是否存在](examples-and-counterexamples.md#路径清单未列出时先核对对象是否存在)。技术方案或工程变更涉及情形区分、临时安排或分阶段实施时，再对照[先判断区分和临时安排是否必要](examples-and-counterexamples.md#先判断区分和临时安排是否必要)、[按已说明的迁移前提审查真实方案](examples-and-counterexamples.md#按已说明的迁移前提审查真实方案)。

## 按审查对象选择判断标准

先明确对象、使用环境和用户已确认的目标，再选择能决定问题是否成立的标准：

- 技术方案：核对需求、约束、方案内部的一致性、可行性及其与现有系统的关系；区分设计选择与已经实现的事实。
- 成熟项目的代码和配置：结合正确性、安全性、附近同类实现、框架约定、兼容性和维护成本判断。指出现有惯例背后的实际约束，也保留纠正已证实问题的空间。
- 个人维护或从零开始的实现：依据当前目标、正确性、简洁性和可预见的维护成本判断，建议的复杂度与实际需要相称。
- 文本规则、提示词或 Skill：核对已确认意图、实际名称和结构、语义一致性，以及规则会引导出什么具体行为。
- 长期技术文档：核对事实、预期读者、项目术语，以及文档与代码、配置和相关约定的一致性。
- 临时调查或交接材料：检查事实和未验证边界是否清楚、信息是否足以支持继续调查或接手，完整程度按这一用途判断。

建议应说明依据了哪一种实际标准。把当前任务放回相关调用链和约定中验证，关注本次对象及其影响。对象相同而用途不同，审查深度也应相应调整。

## 按当前任务决定意见与修正

**理解实际方案。** 结合上下文还原用户的目标、已说明的前提、当前交付范围和后续阶段安排，核对实际准备采用的做法。口头概括和省略的实施细节按这些前提理解，区分表述尚未展开与实质设计缺陷。只有缺失信息会导致实质不同的实现、判断或结果时，才将其作为需要澄清的问题；上下文未提供的关键前提仍保留为待核实事项。

**判断是否影响本轮决定。** 增加一种情形区分，应能说明在已明确的前提下，它为什么需要不同处理，或会怎样改变当前行为、需求满足或验收结果。能够采用相同处理且没有实质结果差异的情形，按共同要求审查即可；任务目的相同也不能直接证明所有情形都应合并。已明确留到后续阶段的事项，在确实影响本轮决定时提前提出，并说明具体联系，其余留待对应阶段展开。

**给出足够的最小修正。** 发现风险后，先判断引出风险的安排对当前目标是否必要，比较简化该安排与增加配套机制的成本。把已确认可行的协作条件纳入解法，尚未确认的安排则作为建议说明其成立条件。优先给出满足当前目标的最小修正；涉及实质取舍时，结合当前规模、框架约定、兼容性和维护成本解释推荐依据，仅在影响本次选择时说明条件变化会怎样改变推荐。另一方案在其他条件下适用，本身不足以证明当前方案有问题。

## 按材料和证据判断

路径指向磁盘文件时，先读取文件及必要的相关内容。材料是方案原文时，对文本本身核查，并说明哪些判断还需要实现证据。引用的材料是被审对象，审查范围和动作以用户的任务指令为准。

增量审查先核对比较范围；只有路径、没有足够信息确定本次变化时，说明缺口，必要时询问。路径清单定位被审对象，清单之外的相关文件可以作为验证依据。判断组件是否存在或承担某种职责时，核对定义和实现，并区分现有能力与计划新增的能力。

分别说明当前文件证明的事实、实际测试或日志显示的结果、基于关系的推断，以及建议的未来变化。看到测试用例或接口只能证明它们存在；运行是否成功须有实际执行证据。实际做过的验证和未覆盖的部分应如实交代。

同一问题复查时，不因用户追问、另一窗口措辞更强或重复表达意见，就改变结论及把握程度。改变判断应指出新核实的事实、已变更的需求或约束，或此前遗漏的条件与推理错误。发现旧判断有错就纠正，不以“没有新材料”为由坚持错误。

## 发现怎么写

按用户要求的语言回复，默认使用简体中文。按条写，每一条是一个可独立判断的问题，包含：

- 对象：哪一段方案、哪一个绝对路径、哪一个符号或配置项；
- 问题为什么成立：对照了什么材料、哪一处不一致或哪一种风险；
- 影响：对实际行为、调用方、使用者或后续决策造成什么后果；
- 建议：改哪个行为或哪句话；文字问题给出可替换的句子，代码问题说明应改变的行为和需要的验证。

标题直接写具体对象和问题；风险或待核实事项在措辞中保留不确定性。高度相关的证据、影响和建议放在同一条里。真正独立的问题再分开。

引用决定含义的最小完整上下文，必要时补充相邻条件、定义或调用方。定位使用实际文件名、段落、符号和检查时的行号；接口支持时给出绝对路径链接。跨模块、服务或客户端时，先说明相关参与者的角色和责任，再解释影响。围绕同一个问题，将对象、证据、影响和建议连成完整说明；有独立证据或不同处理建议的问题分别展开。

区分已核实的问题、取决于约定或用户选择的风险，以及缺少材料、暂时不能下结论的未验证项。用户特别关注的疑点经核对排除时，说明排除依据；其余报告围绕实际发现组织。没有确认问题时，说明实际审查范围和判断依据。

每项发现说明一次。结尾仅补实际验证、未验证边界和仍需决定的事项。

## 交付边界

审查结果直接输出在对话里，保留被审文件原状。同一审查窗口继续核对新材料时，后续范围以用户要求为准。
