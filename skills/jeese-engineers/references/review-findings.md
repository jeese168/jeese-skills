# 审查窗口根据用户拼好的材料写发现

对照少样本：[审查窗口只写发现的问题](examples-and-counterexamples.md#审查窗口只写发现的问题)、[每一条发现都能单独点头或反驳](examples-and-counterexamples.md#每一条发现都能单独点头或反驳)。

## 用用户贴来的材料工作

用户会手动拼好提示词。常见两种包装：

- 窗口里直接打出的技术方案：用固定格式包起来，并说明这是引用的原始材料，需要审核；
- 已经落盘的文件：情况一列出的绝对路径，加上这些路径在任务里的说明，再用固定格式包起来。

后面会拼上执行窗口生成的审查指令。以用户这一次贴进来的材料、路径和指令为准。路径指向磁盘文件时，读取这些文件再下判断。材料是方案原文时，对方案文本本身审查，并标明哪些判断还需要对照尚未提供的实现。

## 发现怎么写

按条写。每一条是一个可独立判断的问题，包含：

- 对象：哪一段方案、哪一个绝对路径、哪一个符号或配置项；
- 问题为什么成立：对照了什么材料、哪一处不一致或哪一种风险；
- 影响：读者、实现或后续 Agent 会怎样被带偏；
- 建议：改哪个行为或哪句话；文字问题给出可替换的句子，代码问题说明应改变的行为和需要的验证。

标题直接写具体对象和已经确认的问题。高度相关的证据、影响和建议放在同一条里。真正独立的问题再分开。

区分已核实的问题、取决于约定或用户选择的风险、核对后不构成问题的排除项，以及缺少材料、暂时不能下结论的未验证项。没有问题时，说明实际审查范围和判断依据。

## 这一窗口交什么

直接把发现打在对话里。同一窗口里用户只用很短的话要求再审一轮时，仍按本文件：对新给出的修改记录或结论继续写发现。
