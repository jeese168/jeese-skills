# 精确修改的讲解示例

本文件用于情况五需要展示前后变化时的校准。场景和源码标识均为虚构。用户只问某一个点时，仅选解释该点所需的内容。

## 先确定修改前材料对应的是哪次任务

当前结果以实际文件为准，修改前内容来自能够对应本次任务的差异、版本记录、原文或可靠的任务记录。说明实际采用的来源；准确原文无法恢复时，保留不确定性，只解释已核实的当前结果和可确定的变化。

例如，P4 已打开文件及其 changelist 可能包含一个长期需求的累积修改，与 depot 或 have revision 的差异也未必只属于最近一次对话。用用户指定范围和可靠的编辑记录锁定本次对象，再用版本记录核对。Git 文件混有早先未提交修改时，同样处理。

## 只给结论不足以理解变化

反例：

> 重试逻辑已经优化，次数可配置，更加灵活，测试也过了。

这段话没有说明哪个对象改了、由谁决定次数、读取哪项配置，也没有可核对的验证结果。

## `runtime/retry.go` 的 `NewRetryPolicy` 改为读取服务配置

假设本次修改前的代码已从对应版本核实：

```go
func NewRetryPolicy() RetryPolicy {
    return RetryPolicy{MaxAttempts: 3}
}
```

当前文件中，构造函数接收启动时加载的服务配置 `ServiceConfig`：

```go
func NewRetryPolicy(cfg ServiceConfig) RetryPolicy {
    return RetryPolicy{MaxAttempts: cfg.Retry.MaxAttempts}
}
```

`ServiceConfig.Retry.MaxAttempts` 表示最大尝试次数。假设相关解析代码和调用链已核实：它在传入前完成正整数校验。此处的变化是次数由配置决定，其余退避逻辑仍由原有字段控制。解释时将这些前提与变化放在一起，用户才能判断为什么这里没有再做一遍校验。

若只读到了默认值和自定义值的测试用例，就说明用例覆盖的意图、尚未执行；若实际执行过测试，再报告命令、结果和验证范围。

这段讲解把具体对象、前后变化、相邻逻辑和证据连在一起。代码块较长时，可以缩短引用，但应补足决定含义的条件和关系。
