# 独立核查指定的已有技术文档

适用于用户明确要求检查已有技术方案、技术笔记或 OpenSpec 文档是否仍符合相关代码、约定或适用外部资料。这里直接完成核查并报告。为当前方案或改动生成另一窗口使用的审查指令，属于情况二。

对照少样本：[送审与独立核查按用户要的产物区分](examples-and-counterexamples.md#送审与独立核查按用户要的产物区分)、[独立核查文档需要明确意图](examples-and-counterexamples.md#独立核查文档需要明确意图)、[文档与实现不一致时分别核对依据](examples-and-counterexamples.md#文档与实现不一致时分别核对依据)。

## 明确对象与核查目的

按用户指定的绝对路径读取文件，包括当前工作区之外的笔记和方案。结合用户的问题确定要核对的是实现现状、约定是否一致，还是外部技术信息是否仍适用。

材料和上下文足够时直接核查；缺少会改变判断的对象、关联项目或适用版本，且无法从现有材料确定时，针对缺口询问。读取失败时说明具体缺失，保留尚未核实的边界。

这条路由由明确的独立文档核查意图触发。仅给了一个 Markdown 路径而意图不明时，先问用途；普通开发中发现文档可能过时，按当前任务范围处理，不自行切换到独立核查。

## 按文档的实际作用核对

先判断文档描述的是当前事实、已确认的目标、尚未实施的提议，还是某个历史版本。核对与问题有关的代码、配置、关联文档和已确认决定，找出差异对应的实际对象及其依据。

OpenSpec 文档按项目中的实际用途、状态和关联关系判断。例如提议中的行为可能尚未实现；描述现行行为的文档则需要与实现现状相对应。检查只报告差异及建议，不自动推进计划、同步规格、勾选任务或归档变更。

涉及外部技术信息时，核对项目实际使用的版本和文档所述条件；需要查证时优先使用适用版本的官方文档等一手来源，注明来源和适用范围。新版行为与旧版行为不同，不自动说明使用旧版的项目文档有误。

## 解释差异，再建议怎样处理

依据核对结果说明差异属于什么情形：

- 已确认的需求或实现发生变化，而文档仍记录旧行为：指出需要更新的具体段落和依据。
- 文档记录的约定仍有效，但实现偏离：指出实现侧的差异和需要确认的决定。
- 文档在描述提议、未来计划或历史状态：按其用途判断表述是否清楚，保留相应时态和范围。
- 外部事实变化或证据不足：说明适用条件、已验证内容及缺口，再给出有条件的建议。

这些情形帮助解释判断，不是要求每次输出四组分类。按实际发现组织，只展开本次存在的问题。

## 输出核查发现

读取并使用 [review-findings.md 的证据要求](review-findings.md#按材料和证据判断)及[发现组织方式](review-findings.md#发现怎么写)。每项发现让用户能看懂哪份文档的哪句话与什么依据不一致，以及建议修改哪一侧、或先确认什么。

结果直接回复在对话里，说明实际核查和未验证的范围。这一轮交付发现与建议；修改文件由用户后续指令决定。
