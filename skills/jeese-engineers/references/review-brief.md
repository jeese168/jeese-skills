# 生成给审查窗口用的指令

对照少样本：[审查指令客观并写清本轮怎么审](examples-and-counterexamples.md#审查指令客观并写清本轮怎么审)、[增量审查指令交代文件内部的比较范围](examples-and-counterexamples.md#增量审查指令交代文件内部的比较范围)。

## 时机和产物

用户在改完、输出完之后点名，包括情况一的路径已经整理完之后再点名。这一轮只生成审查指令，直接打在对话里。

这份指令是给**另一个窗口里的审查 Agent** 用的。用户会把它和原始材料或路径清单拼在一起。指令写完，这一轮就结束。

## 指令里应写清的内容

按当前任务当场写，写成本轮能直接粘贴使用的说明，包含：

1. **被审对象会以哪种形式出现。** 用户可能把窗口里直接打出的技术方案用固定格式包成「引用的原始材料」；也可能把情况一列出的绝对路径和路径说明包在一起。两种都要能审。对象是用户贴来的材料或路径指向的文件，以那份材料为准。
2. **本轮审查范围。** 用户已经选定增量或全量的，把这个范围及对应任务写进指令。增量按下节交代可核对的比较范围；全量审这些路径所覆盖的、与当前功能相关的全部已落盘内容。用户在材料里另有更窄指定的，以用户指定为准。
3. **审查所需的背景与判断依据。** 把影响本次判断的最小必要背景直接写进指令：要解决的需求、用户已确认的约束和预期行为，以及仍待确定的事项。将执行 Agent 自己选择的实现做法标为待审选择，并给出可核对的依据。另一个窗口应能凭这份指令和用户拼接的材料理解任务；需要补充阅读时，指出具体来源。判断标准按当前对象选择，包括用户已确认的意图、真实文件、方案的一致性和可行性。
4. **结论怎么写。** 要求按条写发现。每一条写清：具体对象、问题为什么成立、它会造成什么影响、建议怎么改。没有问题时，说明实际审了哪些、凭什么认为没问题。
5. **这一窗口的职责。** 审查窗口只报告发现，直接输出在对话里。

## 增量审查需要可核对的比较范围

文件路径确定审查对象，比较范围确定对象里哪些变化属于这次任务。按实际证据交代修改前后对应关系，可以使用已确认的提交范围、任务对应的 diff、相关符号及其具体变化、或可靠的修改前材料。所选来源应能让另一个窗口找到并核对本次变化；来自对话的必要信息应在指令中带过去。

Git 工作区差异、P4 已打开文件或变更列表可能包含多次任务的累积修改。先核对任务归属，再描述本次增量。审查相关调用链和相邻代码可用于验证这些变化，发现范围仍以用户指定为准。

证据不足以恢复准确边界时，写明已确认的部分和缺失的比较材料，并说明哪些结论暂时无法验证；边界缺失导致本次增量审查无法开展时，针对缺失范围向用户询问。用户选择全量后，再按全量生成指令。

## 客观

指令站在审查方，按材料和文件能否核实来写。执行窗口自己做过的选择，写成审查方需要核对是否成立的对象，并指出可以核对的材料位置。

当前任务里仍不确定、需要产品或他人拍板的点，在指令里标明为待核对项，让审查窗口看见边界。
