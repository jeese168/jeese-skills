# 学习笔记与技术理解文章

适用于把阅读、试用、对话、代码探索或产品体验整理成一篇可独立阅读的文章。文章记录的是已经形成的认知，不复制探索过程的时间线。

## 先确定文章要解决的理解问题

用一句内部工作句确定目标，例如：“让没有使用过 GitHub 协作的人理解 PR 中各角色和状态的关系。”这句话用于筛选材料，不必写进正文。

列出读者理解目标所缺的前提，并按依赖关系排序。先讲会阻塞后文的概念，再讲建立在它上面的机制。不要按照作者当时提问、误解、纠正和补充的顺序逐轮复现。

如果学习过程里出现了有价值的误解，可以把它重写为正文中的对比或边界：先给正确模型，再说明为什么常见直觉会错。不要保留“我刚才又想到”“另外再补一点”之类对话残留。

## 选择适合主题的主线

不同主题可以使用不同主线：

- 概念系统：对象及其关系 → 各对象的职责 → 一次完整运行过程；
- 工具体验：它解决什么问题 → 实际操作链 → 可观察结果 → 限制与适用场景；
- 机制理解：现有问题 → 内部机制 → 正常路径 → 失败路径 → 代价；
- 多方案比较：共同目标 → 比较维度 → 差异 → 条件化选择；
- 个人复盘：原有理解 → 关键证据或体验 → 修正后的模型 → 仍未确认的部分。

主线只选一个。其他结构作为局部工具嵌入，不要让文章同时沿时间、功能、界面和抽象层级四条线来回切换。

## 解释产品、平台和协作流程

对每个关键动作写清楚：谁执行、在哪执行、操作什么对象、对象如何变化、结果由谁使用。例如解释 PR 时，应分别说明提交者、审阅者、仓库维护者和自动化系统的动作，不能把它们都写成“你”。

界面名称只是入口，不是解释。读者需要知道按钮背后的状态变化和权限边界。能用一条具体流程串起多个概念时，先建立对象关系，再走一遍真实流程。

## 使用例子、命令和图

例子应尽量来自实际经历、真实项目或可验证操作。它要帮助读者观察一个状态变化，而不是只把名词换成生活物品。

命令和代码只保留支撑理解或复现所需的最小片段。写清执行位置、前置条件和可观察结果。截图用于证明界面状态时，正文应点出读者需要看的区域。

当三个以上对象存在稳定关系，或一次流程跨越多个主体和位置时，可以使用一张小表、流程图或层级图。视觉材料不应重复已经足够清楚的短段落。

## 收束文章

结尾只处理文章真正留下的结果：形成了什么可用认知、实际应如何选择、哪些问题仍待验证。不要把全文标题重新念一遍，也不要增加泛化的“未来展望”。

发布前检查：

- 删除问答编号、面试语气和聊天顺序；
- 确认术语第一次出现时已经够用；
- 确认关键流程中的主体没有被“你”吞掉；
- 合并意义重复的结论和小节；
- 将仅仅因为“看起来完整”而加入的旁支删掉；
- 对可能变化的产品行为、版本和设置进行当前验证。
