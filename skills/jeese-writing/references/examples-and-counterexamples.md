# 正例与反例

这些例子展示判断方式，不是可复制的固定句型。

## 开头直接进入对象

反例：

> 当然可以。下面我们将从多个角度全面、系统地介绍 Worktree，帮助你深入理解这一强大功能。

正例：

> Worktree 是 Git 给同一个仓库创建的另一套工作目录。它有独立的文件和当前分支，但与主目录共享提交历史，因此两个任务可以同时修改代码，不需要来回切换目录中的分支。

正例先建立对象、差异和直接作用，没有承诺式铺垫。

## 不把所有角色都写成“你”

反例：

> 你把 PR 设为 Ready 后，检查通过，你就可以自动合并。

正例：

> PR 提交者把 Draft 改为 Ready，表示修改已经可以接受审阅；仓库的审阅者随后给出批准或修改意见。满足分支保护和 CI 条件后，拥有合并权限的维护者可以手动合并；如果仓库允许自动合并，维护者也可以提前启用它，让 GitHub 在条件满足时执行合并。

正例分别交代提交者、审阅者、维护者和 GitHub 自动化的动作、权限与结果。

## 口语化要推动理解

过度书面：

> 该机制旨在通过工作目录隔离实现并发开发活动的协同开展。

过度表演：

> 说白了这玩意儿就是 Git 又给你整了个房间，简直爽爆了。

合适：

> 说白了，Worktree 解决的是“我不想为了做另一件事，把当前目录切走”这个问题。它没有复制一套 Git 历史，只是给同一个仓库增加了另一套可同时存在的文件。

合适的口语先把问题压缩成人能感知的困境，随后立刻回到精确边界。

## 列表不能代替论述

反例：

> Worktree 的特点：
> - 隔离
> - 高效
> - 方便
> - 适合 AI

正例：

> 人工开发时，切换分支通常已经够用；但切换要求当前目录处于可切换状态，未提交修改、正在运行的服务和本地生成文件都会增加摩擦。Agent 往往需要在后台同时执行多个长任务，Worktree 让每个任务拥有独立目录，所以这个原本就存在的 Git 功能在 Agent 场景里更常见。

正例给出了条件、机制和为什么场景变化会改变选择。

## 不重复收束

反例：

> 因此，Skill 提高了流程稳定性。
>
> 换个角度看，Skill 的核心价值就是让流程更稳定。
>
> 总结来说，Skill 本质上是一种稳定流程的方法。

正例：

> Skill 把可复用的工作方法放进按需加载的指令包。它仍由模型解释和执行，因此适合需要判断的流程；必须无条件发生的检查，应交给 Hook、CI 或普通脚本。

一句结论同时交代能力与边界，不需要再从另一个角度复述。

## 标题服从语义层级

反例：

> ### Worktree 是什么
> #### Worktree 的定义
> ##### Worktree 的核心概念

三个标题实际上指向同一件事。

正例：

> ### Worktree 解决的工作目录问题
> #### 分支切换为什么不够
> #### 多个目录如何共享仓库历史
> ##### Agent 并行任务中的实际变化

只有内容确实形成独立、递进的模块时，才增加标题层级。

## 新增内容服从文档生命周期

长期维护文档中的机械追加：

> ### 补充说明
>
> 另外，Worktree 还会共享仓库对象数据库。

如果前文正在解释多个工作目录如何共享历史，这条信息应直接进入对应机制段落，并与已有解释合并。修改完成后不需要保留“另外补充”的时间痕迹。

临时排查记录则不同。按日期追加“新发现”和后续验证结果可以保留调查顺序，也方便交接；只要关系写清，就不需要为了看起来像正式文章而重构全文。

## 技术方案之外保留新的工程选择

已有成熟项目的技术方案已经确认复用当前任务队列。Agent 整理文档时发现，项目中现有的 `BatchWriter` 已经处理了相同的重试边界，而且复用成本很低。

反例是在正文中直接把方案改成使用 `BatchWriter`，或者为了兼容两种可能性，同时加入新的统一写入接口和策略层。这样会把写作过程中发现的选择变成未经讨论的设计决定。

更合适的做法是继续按照已经确认的任务队列方案完成文档，并在文档之外说明：

> 整理方案时发现，项目现有的 `BatchWriter` 已经处理了相同的重试边界，复用成本可能低于重新实现。是否需要先比较两种方式，再决定要不要调整方案？

这条说明只把值得讨论的选择交还给用户，不代替用户修改已经确认的方案。
