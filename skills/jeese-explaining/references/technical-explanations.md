# 技术系统与方案讲解

## 按当前把握补充证据

讲代码库或具体系统行为前，先判断当前上下文是否足以支撑结论。已有信息充分时直接使用；缺少会改变判断的代码、配置或运行证据，而且可以安全获取时，先检查再讲；无法继续验证或当前任务不值得扩大调查时，明确说明哪些部分是推断。

验证强度服务于结论可靠性，不要求为每句话重新打开源码。已经核实并留在当前上下文中的事实可以继续使用，只有证据不足、相互冲突或结论发生变化时才继续补充。

## 区分系统实际存在的层次

讲项目、代码或工程方案时，分清：

- 已经实现、上线或实际执行过的部分；
- 日志、测试、监控或使用中真正观测到的结果；
- 根据现有证据形成的解释和判断；
- 如果重做、规模变化或未来扩展后才考虑的改进。

不要把建议方案讲成现有能力，也不要因为代码里存在某个接口或分支，就假定完整功能已经可用。

## 先建立概念，再使用源码标识

陌生术语或变量名第一次出现时，先给出便于理解的中文语义，再附源码中的准确标识，例如“执行代次（`generation`）”。如果后文需要频繁读代码，可以说明下文沿用该标识；已经建立概念后，不必每次重复翻译。

中文语义用于说明它在系统中的实际角色，不要求生硬直译源码名称。只有当理解依赖运行位置、所有者或相邻对象时，才在当前句段中自然补足这些关系；不要把每个标识拆成固定的归属、输入、输出和影响清单。

多个客户端、进程、服务或运行环境反复交互时，可以使用简短标签帮助定位，但标签必须带有可理解的角色名称，不能只抛出项目缩写。关系已经建立后直接沿用，不在每一步重新介绍全部参与者。

## 让取舍服从现实条件

比较技术方案时，先看当前规模、真实瓶颈、已有基础设施、团队维护成本和失败后果。复杂方案在理论上更完整，不表示当前就更合适；未来扩展可以说明，但不能用极端规模稀释当前事实。

解释一个选择时，指出什么条件让当前方案成立，以及哪些变化会让另一个方案更值得采用。这样给出的是条件化判断，不是脱离上下文的“最佳实践”。

## 解释量化结果

遇到耗时、吞吐量、调用量和提升比例时，说明测量方式、样本范围、比较基线和适用边界。只有少量日志对照、没有压测、多个记录数字冲突或实际业务收益有限时，降低结论强度，不复述最漂亮的数字当作稳定事实。

## 组织分类、比较和代码

分类先说明依据什么维度划分，避免给出一组名称后才让用户猜它们为什么并列。流程按真实执行顺序讲，设计机制和它减少的开销、解决的问题或新增的代价尽量相邻出现。

比较两三个对象时，可以分别讲清机制后给出条件化选择；对象或维度较多时，再使用表格统一比较机制、性能、成本、场景和限制。不要先列一遍完整分类，再换一种形式重复相同内容。

代码用于证明语义、条件或状态变化。先说明代码要证明什么，只给支撑理解所需的最小片段，再指出关键行、可观察结果和适用边界。不要用长代码替代解释。

需要从业务现象追到线程、锁、存储、网络或系统调用时，可以跨层讲解，但每次下钻都要说明上一层现象为什么指向下一层机制，不能只堆底层术语。

当实际行为容易被误认为 bug，或明显违背用户当前的直觉时，说明通常会预期什么、实际发生什么、机制为什么如此，以及它会怎样影响定位问题。把这些内容放进连续解释，不固定生成四个标题。

## 走通机制和故障

复杂系统先建立对象与关系，再选择一次端到端实例走通输入、关键状态、调用链和结果。代码、日志和图用于证明这条路径，不要把原始材料整块倾倒给用户。

故障讲解可以使用“观测信号 → 立即止损 → 根因定位 → 临时绕过 → 根治修改 → 验证结果”的因果顺序，但只讲真实存在的阶段，不为了完整补造操作。
