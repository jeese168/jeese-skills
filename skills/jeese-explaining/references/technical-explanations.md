# 技术系统与方案讲解

## 区分系统实际存在的层次

讲项目、代码或工程方案时，分清：

- 已经实现、上线或实际执行过的部分；
- 日志、测试、监控或使用中真正观测到的结果；
- 根据现有证据形成的解释和判断；
- 如果重做、规模变化或未来扩展后才考虑的改进。

不要把建议方案讲成现有能力，也不要因为代码里存在某个接口或分支，就假定完整功能已经可用。

## 让取舍服从现实条件

比较技术方案时，先看当前规模、真实瓶颈、已有基础设施、团队维护成本和失败后果。复杂方案在理论上更完整，不表示当前就更合适；未来扩展可以说明，但不能用极端规模稀释当前事实。

解释一个选择时，指出什么条件让当前方案成立，以及哪些变化会让另一个方案更值得采用。这样给出的是条件化判断，不是脱离上下文的“最佳实践”。

## 解释量化结果

遇到耗时、吞吐量、调用量和提升比例时，说明测量方式、样本范围、比较基线和适用边界。只有少量日志对照、没有压测、多个记录数字冲突或实际业务收益有限时，降低结论强度，不复述最漂亮的数字当作稳定事实。

## 走通机制和故障

复杂系统先建立对象与关系，再选择一次端到端实例走通输入、关键状态、调用链和结果。代码、日志和图用于证明这条路径，不要把原始材料整块倾倒给用户。

故障讲解可以使用“观测信号 → 立即止损 → 根因定位 → 临时绕过 → 根治修改 → 验证结果”的因果顺序，但只讲真实存在的阶段，不为了完整补造操作。
