# jeese-skills

`jeese-skills` 是一个长期维护的个人 Agent 适配仓库。它把我在理解、组织、解释和表达信息时真正需要的习惯，沉淀为可检查、可修改、可跨模型和跨设备使用的 Agent Skills。

这个项目不是提示词收藏夹，也不准备重新发明所有工作方法。成熟的通用能力可以直接站在巨人的肩膀上；本仓库只保存通用模型和现有工具没有稳定覆盖、而我在真实协作中反复需要的个人适配。

## 本仓库适配 Agent 交互，通用工具负责工程流程

Superpowers、OpenSpec 等成熟方法和工具可以继续负责软件项目怎样讨论方案、制定计划、实施、验证和迭代。`jeese-skills` 不与它们竞争，也不重新设计一套企业级开发流程。

本仓库处理的是另一层问题：Agent 怎样向我建立必要的上下文，怎样讲清对象、关系和判断，怎样把已经完成的修改交付成容易审核的说明，以及怎样按照我的理解和表达习惯形成文档。即使某个 Skill 接触代码或技术方案，它适配的也是人与 Agent 之间的理解、交流和交付，不替代这些工具负责的工程流程。

## 为什么需要个人 Skills

通用模型需要面对大量不同用户，因此通常追求稳定、均衡、客观、完整和可执行。这样的 Agent 很通用，也容易形成趋同的表达方式：先套结构再填内容，把连续思想拆成大量标题和列表，反复总结已经说清的结论，或者为了显得完整而加入当前并不需要的信息。

模型可能掌握了答案，却没有按照我能够自然理解和继续思考的方式讲出来。如果每次都要重新纠正这些默认习惯，真正的理解和表达工作仍然会回到我身上。

`jeese-skills` 要把这部分个人适配从具体模型中抽离。模型可以更新，使用的平台也可以变化，但已经验证过的协作方式由我自己保存和维护。

这些 Skills 不只处理语气和用词，还会逐步说明：什么信息应该先出现，一个概念第一次要讲到什么程度，因果、机制、例子和边界怎样组织，怎样说清主体、对象、动作和影响，以及什么时候应该保留明确判断。

## 仓库保存什么

仓库保存已经从真实任务中提炼出来、会改变 Agent 决策的内容，包括：

- 一种反复出现的个人协作任务应该怎样完成；
- 某种题材需要的局部规则；
- 跨任务反复出现的稳定个人习惯；
- 必要的正反例、参考资料和确定性脚本。

原始聊天、私人经历、未经筛选的个人资料和只对一次任务有效的要求，不会因为“以后可能有用”就进入仓库。真实反馈需要先被提炼成可复用的判断。

## Skills 怎样组织

平台首先根据 Skill 的 `name` 和 `description` 判断是否激活它。Skill 激活以后，Agent 再读取 `SKILL.md`，并按照其中的说明按需加载内部 references。这就是渐进式披露。

```text
用户任务
   ↓
平台选择一个 Skill
   ↓
读取 SKILL.md
   ↓
Agent 根据任务选择内部 references
```

reference 不是另一个 Skill，而是同一个 Skill 的内部资料。组织时遵循以下边界：

| 情况 | 组织方式 |
| --- | --- |
| 主要任务、工作过程和验收标准相同，只有局部差异 | 一个 Skill，通过 references 区分 |
| 用户触发方式、主要产物、工作过程或验收标准明显不同 | 拆成独立 Skills |
| 一个任务必须经过固定的多个阶段 | 在真实需要出现后创建工作流 Skill |

因此，不会为了题材名称不同就立即拆分，也不会建立一个只负责给所有 Skills 分类的总路由。边界由真实任务中的冲突决定。

## Skills 怎样演化

现有文章和历史修改只能提供第一批材料，不能一次性定义全部习惯。Skills 会通过真实使用持续校准：

```text
完成真实任务
    ↓
观察不符合需要的结果
    ↓
判断问题属于哪个层级
    ↓
修改最小范围的规则或例子
    ↓
继续用真实任务验证
```

一次反馈不会自动成为永久规则。当前任务要求留在上下文，题材差异进入对应 reference，跨任务反复出现的习惯才进入稳定规则，可以机械判断的问题才考虑交给脚本。

## 普通版与工作流版讲解

两版由用户按工作习惯自行选择安装、使用，不设默认版本或根据模型表现自动切换。`jeese-explaining` 普通版按需加载内部指导，不强制阶段中间产物或校验脚本；`jeese-explaining-workflow` 面向具备文件与工具能力的 Agent，用实际阶段产物加强执行。两版各自携带运行指导。

普通版提供五种情况：标准讲解、快速了解、针对性解答、源码带读，以及现实问题的解释与判断。前四种对齐工作流的理解目标；针对性解答既承接独立概念问题，也承接追问。普通版的标准、快速保留普通学习与 Bug 诊断讲解的区别，源码带读保留一次交付或用户控制的分段节奏。现实判断用于社会、经济、历史、行为和个人发展等讨论，不按网页或本地平台分流。

普通版示例：

- `使用 $jeese-explaining，标准讲解，按协作与机制的深度说明这个模块。`
- `使用 $jeese-explaining，快速了解这段逻辑，讲到定位与作用。`
- `使用 $jeese-explaining，解释一下回调是什么。`
- `使用 $jeese-explaining，源码带读，从这个入口读到状态更新，按实现与依据的深度分段讲，等我说继续。`
- `使用 $jeese-explaining，结合已有资料解释这个社会现象，比较几种原因的证据。`

### 工作流版的分阶段执行

渐进式披露决定 Agent 在什么时候读取 `SKILL.md` 和对应 references，但不会自动要求 Agent 每读完一层就留下一份中间结果。`jeese-explaining-workflow` 面向具体项目中的代码、模块、系统机制和工程问题，用阶段产物加强讲解过程。两者追求相同的理解目标；社会、历史、日常行为等现实判断由普通版处理，不纳入 workflow。

目前提供标准、快速了解、针对性解答和源码带读四种模式。标准模式有四阶段：查清依据、写出概念与机制、安排图文、生成并核对讲解；快速模式有三阶段：准备必要内容、形成直观草稿、完成并核对讲解。源码带读有四阶段：确定阅读范围、追踪源码与概念、编排伴读说明、交付并保存阅读位置；可一次交付，也可由用户说继续后分段推进。用户决定模式及其切换，Skill 不自动先快后慢。

标准和快速模式从第一阶段区分普通学习与 Bug 诊断讲解，保持各自阶段数。普通学习核对源码语义；Bug 分支结合异常表现、代码及可取得的现场材料查证，区分表现位置、原因位置与需要时的修改建议，不因 QA 指派或异常出现在哪一端就认定归属。没有日志也可以开始；有限定位不能写成根因已查明，建议也不等于实际修复。这个分支适配诊断中的理解与讲解，不授权修改项目代码或替用户决定跨模块的工程取舍。

标准、快速和源码带读的中间产物使用 Markdown。根目录来自本次明确要求或当前 Agent 适用的用户级规则；没有约定就询问。在根目录下按任务建子目录，换任务需要另建目录时先问用户。每一阶段留下后续实际要用的内容，再进入下一阶段；中间产物不记录完整内部推理，也不替代用户最终要读的讲解。

局部追问复用针对性解答，不重跑完整流程。独立概念问题不强制落盘；已有任务中，只有新事实、纠正或范围变化等影响后续理解时才更新原记录。源码带读的追问保留阅读位置，用户说继续后接回主线。

分阶段产物在自由 Markdown 正文外使用少量模式、阶段和本轮标记，每阶段落盘后运行内置的 Python 3 结构检查脚本。脚本只读指定任务文件，检查截至当前阶段的区块是否存在、非空；需要图时检查文内 PlantUML、Mermaid 或线条示意的代码块，不要求独立图片文件。它不判断概念是否讲清、事实是否正确，也不保证模型实际遵循了执行顺序。格式和调用方式见 [结构检查约定](skills/jeese-explaining-workflow/references/artifact-checks.md)。

中间产物的完整有效内容仍在上下文时直接复用；缺失、截断或发生修订时，可用脚本的 `--read-stages` 按轮次和阶段补读，不每阶段重读整份历史。补读与校验分开：每阶段的真实落盘及 `--through` 校验仍然必需，不能以“上下文已有”或“读取成功”替代。

例如可以显式调用：

- `使用 $jeese-explaining-workflow，标准模式，按协作与机制的深度讲清这个模块；目的是为当前重构建立理解。`
- `使用 $jeese-explaining-workflow，快速了解这组对象的关系，先讲到定位与作用。`
- `使用 $jeese-explaining-workflow，只解释这里的加载版本号是什么意思。`
- `使用 $jeese-explaining-workflow，快速模式，结合这份 QA 描述和日志查清异常，并说明建议改在哪一侧。`
- `使用 $jeese-explaining-workflow，源码带读，从这个入口读到状态更新，按实现与依据的深度分段带我看；等我说继续再往下。`

工作流版不追求覆盖普通版的全部用途，后续按真实需要增加路线。阶段约束用于提高遵循稳定性，不是平台强制保证。子 Agent 审查默认关闭；用户明确要求时，在标准或源码带读第三阶段、快速第二阶段之后调用 `jeese-engineers` 情况六：一个子 Agent 检查中间产物，主 Agent 核实后按采纳／不采纳处理，自行修正并继续最终讲解。不会要求用户搬运审查意见或批准中间修订。必要时最多增加一次聚焦复查；缺少 Skill、情况六或子 Agent 能力时说明限制，不把自检冒充独立审查。

## 工作与学习文档的工作流初版

`jeese-docs-workflow` 是独立的文档工作流，当前 `jeese-writing` 保留。它处理学习、项目和技术方案相关文档，沿用核心写作风格，并用阶段产物、完成条件和实际脚本检查引导后续生成。社会人文文章与随笔不在这份工作流的范围内。

入口结合本次要求和上下文选择新文档、维护或合并。新文档共用准备后，学习与技术方案分别进入独立的四阶段文件；维护与合并各有三阶段指导。各阶段只读取当前需要的方法，达到内容完成条件并通过结构检查后继续。

| 执行路径 | 阶段 |
| --- | --- |
| 学习文档 | 准备内容与依据 → 文章组织 → 完整初稿 → 核对成稿 |
| 技术方案 | 需求与现状 → 确认设计 → 方案初稿 → 核对成稿 |
| 维护已有文档 | 修改内容与影响 → 修订稿 → 写回核对 |
| 多文档合并 | 来源与合并结构 → 合并初稿 → 核对成稿 |

中间文件保留加工后的解释、设计、组织和草稿；完整初稿在后期形成。前阶段的内容按需复用或补读，每阶段落盘后的结构检查仍需运行。最终正文写入约定目标，事实、概念、设计和图文的正确性由各阶段核对，脚本不替代内容判断。两份写作 Skill 都携带各自运行材料，工作流不依赖讲解 Skill 已安装或已执行。

例如：`使用 $jeese-docs-workflow，把这次讨论整理成供执行 Agent 使用的技术方案，目标路径为……，中间产物放在……。`

## 社会分析与随笔的工作流初版

`jeese-essays-workflow` 从已有讨论、AI 复述、条目化草稿或成品文章进入写作。新写、修改和合并共用三阶段：整理原意与主线 → 沿主线完善关键论述 → 形成全文并立即核对修订。前两阶段保留加工后的内容和表达选择，完整文章在第三阶段形成；各阶段分别落盘、核对完成条件并运行结构检查。

指导收拢为入口、核心风格、写作流程、配图与 FIG、打印与导出五份文档。三个阶段集中在同一流程文件，通过产物和检查控制推进；风格短例放在对应规则附近，配图和导出按需读取。

风格以用户认可的随笔样本及明确反馈提炼，保留作者立场、适用的攻击性与比喻，也支持由具体事情引出的自省和认识变化。标题、加粗和 FIG 按本篇表达选择。配图只交付位置、完整生图提示词和图注，不执行生图；已有实体图片可以接入。

用户要求 HTML／PDF 时，使用 Skill 内的打印骨架、CSS 和脚本导出，沿用已认可的 A4 排版与重复页眉。Markdown 转语义 HTML 由 Agent 对照原文完成，脚本组合固定模板、处理实际图片路径并调用现有浏览器打印，最后检查真实页面。模板只保存样式和结构，原始文章与本机路径不是运行依赖。

正文、导出和中间产物位置依次采用本次要求、项目约定及适用的全局规则；仍缺失时集中询问。只给一个路径时按共用目录处理，实体图片默认放在 Markdown 同目录的 `文档图片/`。现有 `jeese-writing` 暂时保留；两份新工作流分别承接工作学习与社会随笔用途，旧版的退役或安装替换另行处理。

例如：`使用 $jeese-essays-workflow，把这份聊天复述写成随笔，保留我的态度与关键比喻，配图只给提示词和 FIG。产物都放在……。`

## 唯一真源与可迁移性

每个 Skill 的唯一源码位于 `skills/<skill-name>/`。平台安装目录、软链接、Plugin 和上传包只是使用或分发方式，不能形成另一份独立维护的源码。

一个可迁移 Skill 必须把运行所需内容全部放在自己的目录中：

```text
skill-name/
├── SKILL.md
├── references/    # 可选
├── scripts/       # 可选
├── assets/        # 可选
└── agents/        # 可选的平台元数据
```

Skill 可以使用 `references/example.md` 这类内部相对路径，因为目标文件会随整个 Skill 一起迁移。它不能依赖 `/Users/...`、跳出 Skill 根目录的相对路径、外部软链接，或者只存在于原电脑上的蒸馏原料。

核心结构遵循 [Agent Skills 开放规范](https://agentskills.io/specification)。平台需要的元数据位于 Skill 内的 `agents/`；Plugin 或其他平台要求的分发文件，只在真实安装或分发需求出现后增加。

## 当前状态

仓库目前有六个处于持续校准中的 Skill：

- [`jeese-writing`](skills/jeese-writing/)：把材料、对话或已有草稿整理成可以长期保存、维护或发布的中文文章和笔记。
- [`jeese-docs-workflow`](skills/jeese-docs-workflow/)：工作与学习文档的工作流初版，新文档包含独立的学习与技术方案四阶段分支，维护和合并各三阶段。
- [`jeese-essays-workflow`](skills/jeese-essays-workflow/)：社会分析与随笔的三阶段写作，交付配图提示词和 FIG，并按需使用内置样式导出 HTML／PDF。
- [`jeese-explaining`](skills/jeese-explaining/)：普通版，提供标准、快速、针对性解答、源码带读与现实判断五种情况，通过按需指导组织讲解，不强制阶段落盘。
- [`jeese-explaining-workflow`](skills/jeese-explaining-workflow/)：面向具体项目的分阶段讲解，提供标准、快速了解、源码带读与针对性解答；标准和快速包含按需进入的 Bug 分支。显式调用，具体流程见上文。
- [`jeese-engineers`](skills/jeese-engineers/)：用户明确调用后，列出增量或全量落盘路径，为当前方案或改动生成完整送审指令，核实返回的意见并分成三类，或按所需深度讲解修改。另有明确触发的低频用途：直接核查指定的已有技术文档或 OpenSpec 文档与相关依据是否一致。情况六接受用户明确要求的 workflow 中间产物独立审查，由主 Agent 调度、核实成两类并修正。审查方按完整指令执行，无需另外加载本 Skill。

讲解产生的定义、因果链、例子和边界可以成为后续写作的原始材料。各 Skill 的基础能力独立运行，指导材料收拢在各自目录内。用户要求的可选审查是明确的跨 Skill 配合：`jeese-explaining-workflow` 在检查点调用当前环境中的 `jeese-engineers` 情况六；不带独立审查的讲解无需这个依赖。`jeese-engineers` 仍支持用户直接调用，也接受用户已授权的情况六交接。

`README.md` 说明项目目的和当前状态；`AGENTS.md` 保存进入仓库工作的 Agent 必须长期遵守的稳定原则。

## 本地使用与同步

本地 Agent 的发现目录应链接到 `skills/` 中的唯一源码，`archive/` 不作为发现或安装来源。建立链接前必须先检查目标，不能覆盖未经确认的实体目录。

仓库通过私有 GitHub 保存版本：一台电脑修改并推送后，其他电脑拉取同一份源码。不同平台可以使用不同安装方式，但不分别维护 Skill 内容。
